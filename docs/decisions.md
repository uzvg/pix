# 技术决策记录

> 本文只记录“为什么”。具体行为以 [architecture.md](architecture.md) 为准。

## D1. 独立 CLI，无仓库依赖

**决策**：`pix` 是通用工具，只接收显式传入的路径和远端，不读取仓库配置。

**原因**：图片压缩和云同步本身与项目类型无关。独立后 Windows 也能用，任何目录都能作为源，不需要仓库上下文。

## D2. 使用 `pyvips[binary]` 绑定，不 shell 调用 `vips`

**决策**：通过 `pyvips.Image.thumbnail(...)` 和 `write_to_file(...)` 完成压缩。

**原因**：`pyvips[binary]` 自带 libvips，`uv tool install` 会把原生库一起装好，Windows 不需要单独下载。已在 pyvips 3.2.0 / libvips 8.18.7 下验证输出与 vips CLI 字节一致。

**影响**：不依赖系统 `vips` 命令；但 `pyvips[binary]` 与系统 libvips 版本不一致时可能有细微输出差异，见 D17。

## D3. AVIF 通过 `heifsave` 保存

**决策**：输出文件使用 `.avif` 后缀，让 libvips 自动选择 `heifsave`。

**原因**：libvips 8.18.7 没有 `avifsave` action，不能按名字调用。临时文件也必须以 `.avif` 结尾，否则格式选择会出错。

## D4. 仅标准库 + pyvips

**决策**：不引入 click、rich、colorama，也不额外封装 argparse。

**原因**：依赖少，安装体积小，跨平台行为可控。argparse 足够表达当前 CLI。

## D5. 第一版单模块 `cli.py`（已由 D27 取代）

**决策**：第一版所有逻辑放在 `src/pix/cli.py`；只有文件承担多个独立职责时才拆分，不按行数拆分。

**原因**：第一版功能规模小，提前拆包只增加跳转成本；行数不是职责的度量。拆分时保持 `cli.py` 为组合根。

## D6. 延迟导入 pyvips

**决策**：`import pyvips` 只出现在 `shrink` / `doctor` 内部。

**原因**：`mirror` / `publish` 不需要图像后端；缺少 libvips 时同步仍应可用。导入失败只在真正需要图像能力时提示。

## D7. 配置优先级：命令行 > 配置文件 > 内置默认

**决策**：三层合并，只有显式传入的命令行参数才覆盖配置。

**原因**：行为可预测，用户能保留全局默认。实现上 argparse 默认值必须为 `None`，否则会压过配置文件。

## D8. `-q` 只表示 quality，安静模式用 `--quiet`

**决策**：quiet 不提供短选项。

**原因**：`-q` 在图像工具里通常表示质量，再复用作 quiet 会产生歧义。

## D9. 尺寸后缀按 1024 进制

**决策**：`500K`、`1M`、`2G` 分别等于 500×1024、1×1024²、2×1024³ 字节。

**原因**：与文件大小语义一致，避免“KB 是 1000 还是 1024”的反复解释。

## D10. 使用 `--min-size`，第一版不保留 `--max-size` 别名

**决策**：参数名为 `--min-size`，配置键为 `min_size`。

**原因**：语义是“小于该值跳过”，`--max-size` 容易被理解为输出尺寸上限。两个名字并存会让规格和测试复杂化；有真实兼容需求时再加别名。

## D11. 使用 rclone bisync 双向同步

**决策**：`mirror` / `publish` 都调用 `rclone bisync`，不使用单向 `copy` 或 `sync`。

**原因**：两边都可能新增、修改或删除文件，单向同步会让另一侧的改动被覆盖或永远无法回流。

**影响**：`mirror` / `publish` 是双向镜像，不是单向备份；删除会双向传播，误删不可逆。用 `--dry-run` 预览、`--resync` 显式重建基线，并默认 `--max-delete 10`（rclone bisync 的删除百分比，`0` 禁止删除，`-1` 不限制）来控制风险；`pix` 只在目标为空时自动 resync。修改排除项后仍必须显式 `--resync`。

## D12. 不内置 rclone 排除规则

**决策**：`pix` 不硬编码镜像排除项；排除全部由 `--exclude` 传入。配置排除项在前，命令行排除项追加在后并去重。唯一例外是 `publish` 固定排除 `.pix/**`。

**原因**：排除项属于调用方的同步策略。`.pix/**` 是 `pix` 自己的状态文件，不属于用户内容，必须排除，否则会被传到图床。合并而不是覆盖，避免加一条规则时丢掉另一条。

## D13. 临时文件 + 原子替换，单文件失败隔离

**决策**：编码到同目录临时文件，成功后 `os.replace`；失败清理临时文件并继续处理其他文件。状态文件同样先写临时文件再替换。

**原因**：中断不会留下半截 AVIF 或半截 JSON；单个坏图不会中断整批，最后通过汇总和退出码 1 报告失败。

## D14. `subprocess.run(list)`，退出码透传

**决策**：不经过 shell，`mirror` / `publish` 直接返回 rclone 的退出码。

**原因**：避免 shell 引号和 Windows 路径转义问题；透传退出码便于脚本判断 bisync 的具体失败原因。这是全局 `0/1/2` 约定的明确例外。

## D15. 日志走 stderr，退出码 `0/1/2`

**决策**：阶段信息、汇总、详细日志都写 stderr；`doctor` 报告、`--dry-run` 计划列表和 `--urls` JSON 写 stdout。

**原因**：stdout 留给可消费的结果，stderr 留给诊断信息；退出码区分成功、运行失败、参数/配置错误。

## D16. 第一版范围收敛

**决策**：不实现 `pix run`、crop、并发压缩、无条件自动 resync、远端探测、彩色日志。

**原因**：这些能力不是完成“压缩 + 双向同步 + URL 输出”闭环的必要条件。先交付可用版本，避免范围膨胀。

## D17. 接受 AVIF 字节差异风险，发布前抽样复验

**决策**：以单张测试图的字节一致性作为当前验证依据，发布验证阶段再用真实图片抽样对比。

**原因**：pyvips 与系统 libvips 版本不一致时输出可能有细微差异，无法在单元测试中穷举。把复验放在发布验证阶段，成本低于过度测试。

## D18. 配置错误与缺失的区分

**决策**：默认配置路径不存在时使用内置默认（`doctor` 显示 `missing (using defaults)`）；显式 `--config` 指向的文件不存在或解析失败时退出 2。`doctor` 同时发现配置错误和依赖缺失时，以 2 优先。

**原因**：默认配置是可选文件，缺失不应算错误；显式指定的文件找不到则是用户输入错误。退出码优先级保证调用方能稳定区分配置问题和环境问题。

## D19. 文档按职责拆分

**决策**：`architecture.md` 是行为规格唯一事实来源；`decisions.md` 只存理由；`development.md` 存环境、测试、构建；`roadmap.md` 存未完成事项。

**原因**：每类信息只有一个落点，避免多份文档互相矛盾。

## D20. 增量状态放在输出目录

**决策**：状态文件固定为 `OUT/.pix/state.json`，记录源/输出的 size、mtime_ns 和参数指纹。`out_mtime_ns` 仅用于诊断，不参与跳过判断。状态每成功 200 个文件刷新一次，并在 `finally` 中原子写入。

**原因**：状态和产物绑定，删除输出目录即重置，不会留下指向不存在产物的全局缓存。参数变化时指纹不匹配，整批重编码，避免“改了 quality 但旧图不更新”。不在跳过条件里比较输出 mtime，避免外部 `touch` 或同步工具改变时间戳后触发无谓重编码；分阶段落盘让 Ctrl-C 不丢已完成进度。

**影响**：首次运行没有状态，会全量编码一次；状态丢失只会导致重编码，不会产生错误结果。

## D21. mirror 与 publish 分离

**决策**：两个子命令，而不是一个带模式开关的 `sync`。

**原因**：镜像原图和发布压缩图的目标、源、默认排除不同。分开后每个命令只有一个明确意图，也不需要 `--delete` 这类容易误用的开关。

## D22. URL 清单默认关闭

**决策**：只有显式 `--urls` 或配置 `[publish].urls = true` 时才生成 JSON URL 清单，且必须有以 `http://` 或 `https://` 开头的 `base_url`。`--no-urls` 可临时关闭配置里的 `true`。

**原因**：不是所有图床都有稳定公开域名。默认关闭可以避免猜测 URL；未配置域名时直接报参数错误，比输出错误链接更安全。布尔参数需要双向开关，否则配置文件打开后单次运行无法关闭。

## D23. 目标为空时自动 resync，非空时显式确认

**决策**：`pix` 在调用 bisync 前探测目标：应用排除项后没有任何条目时自动加 `--resync`；目标非空时不自动加，缺少基线导致的失败原样返回并提示用户显式 `--resync`。`--allow-empty` 的操作仍要求显式 `--resync`。

**原因**：resync 会在两边都有内容时以一侧为准覆盖另一侧。目标为空时没有任何远端内容可覆盖，自动初始化不会造成数据损失，还能让首次运行与后续运行使用同一条命令。目标非空时自动 resync 等于替用户决定哪边是权威，风险不可接受，必须显式确认。

## D24. 破坏性操作先拒绝空输入与目标冲突

**决策**：`shrink --prune` 扫描到 0 个源图片但状态仍有条目时拒绝删除；`mirror` / `publish` 源为空时要求显式 `--allow-empty` 且同时带 `--resync`；两个源文件映射到同一输出时退出 2。

**原因**：空目录最常见的来源是挂载失败、路径写错或上游失败，而不是用户真的想删除全部。目标冲突（如 `a.jpg` 与 `a.jpeg`）会让后一个编码静默覆盖前一个。这些情况都应在写入或删除前拒绝。

## D25. shrink 单实例锁

**决策**：非 `--dry-run` 的 `shrink` 在 `OUT/.pix/lock` 上使用 `O_CREAT|O_EXCL` 创建锁，退出时在 `finally` 删除。锁已存在时返回 1 并提示检查另一个进程或删除陈旧锁。

**原因**：两个并发 `shrink`（例如 cron 重叠）会写同一批输出和状态，最后写入者获胜，结果混合。rclone 自己会锁 bisync 工作目录，`shrink` 没有对应机制。

## D26. rclone 版本在命令入口检查

**决策**：`mirror` / `publish` 启动时执行 `rclone version` 并要求 `>= 1.66`；`doctor` 保留同样的检查作为诊断。

**原因**：旧版 rclone 的 bisync 参数或行为不同，只靠 `doctor` 会让直接运行同步命令的用户遇到晦涩错误。版本检查放在真正调用 rclone 之前，失败信息才可操作。

## D27. 按职责拆分 `cli.py`

**决策**：`cli.py` 只保留参数解析、子命令分派和组合根职责；配置、日志、`shrink`、rclone 基础设施、`sync` 命令和 `doctor` 分别放在同包模块中。

**原因**：四个子命令已覆盖配置、压缩、同步和诊断等独立职责，继续放在单文件里会让阅读和修改反复跳转。拆分按职责而不是行数；`cli.py` 仍是唯一组合根，低层模块不反向依赖它。

## D28. 默认配置用内置模板生成

**决策**：随包分发的 `src/pix/default_config.toml` 是默认值的唯一来源：`load_settings` 通过 `load_defaults()` 解析它，`pix config init` 直接复制它（保留注释）。目标文件已存在时拒绝覆盖并退出 2，`--force` 才覆盖；该命令在 `load_settings` 之前分派。

**原因**：Python 3.11 标准库只有 `tomllib`，没有 TOML 写入器；引入 `tomli-w` 违反“仅标准库 + pyvips”的约束。独立文件可以直接带注释，用户打开就能改，编辑器也能按 TOML 高亮；默认值只在这一处维护，避免代码常量与模板漂移。拒绝覆盖保护用户已经修改过的配置，误覆盖的代价远高于多敲一个 `--force`。提前分派让 `--config` 指向新路径时也能创建工作，而不是被“config file not found”挡住。

## D29. `backup` 改名为 `mirror`

**决策**：原 `backup` 子命令改名为 `mirror`，配置节 `[backup]` 同步改为 `[mirror]`，`publish` 保持不变；不保留旧名别名。

**原因**：`backup` 暗示单向、只增、可回滚，但实现是 `rclone bisync` 双向镜像，删除会双向传播且不可逆，命令名本身就在误导用户。`mirror` 准确描述机制。`publish` 描述的是目的，不隐含“远端只增”，取消发布时删除传播符合直觉，因此保留。处于测试阶段且未发布，改名成本最低。

**影响**：破坏性改名，不提供旧命令名或旧配置节兼容。

## D30. pix 负责目标目录，不泄漏 rclone 前置条件

**决策**：`mirror` / `publish` 在 bisync 前执行 `rclone mkdir DEST`（幂等），再用 `rclone lsjson DEST --max-depth 1` 判断目标是否为空。用户不需要手动运行 rclone 创建目录。`--dry-run` 同样执行这两步，但只可能留下一个空目录，不传输或删除文件。

**原因**：bisync 要求 Path1 和 Path2 都已存在，但这是 rclone 的实现细节，不是用户的概念。要求用户先手动 `rclone mkdir` 会把工具的内部机制泄漏到使用流程里。统一由 `pix` 管理目标目录，本地路径和 remote 走同一条代码路径，不需要解析 remote 语法。判空只列一层并应用与 bisync 相同的排除项，成本可控，也避免把“只有被排除文件”的目标误判为非空。

**影响**：首次同步不再需要 `--resync`。目标被清空后会从本地恢复，这是保数据的选择，不会删除本地文件。
